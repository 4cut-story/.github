# 설계 결정과 대안

[← 4cut story 소개로 돌아가기](https://github.com/4cut-story)

| 결정 | 고른 것 | 버린 대안 | 이유 |
| --- | --- | --- | --- |
| **조회수를 어떻게 셀까** | 방문자 쿠키마다 세고, 같은 쿠키가 같은 만화를 10분 안에 다시 열면 한 번으로 치기. 봇은 web에서 거르기 | 열 때마다 모두 세거나, 로그인한 사람만 세거나, IP 주소로 사람을 나누기 | 새로고침이나 뒤로 가기마다 오르면 숫자가 부풀고, 로그인한 사람만 세면 링크로 들어온 사람이 빠져요. IP는 같은 와이파이를 쓰는 여러 사람을 한 명으로 보고 개인 정보이기도 해요. 쿠키는 브라우저마다 달라서 로그인 없이도 사람을 나눌 수 있고, 백엔드에는 쿠키의 해시만 저장해요. 중복 판단은 DB 한 문장(있으면 10분 지났을 때만 갱신)이라 동시에 열어도 한 번만 세요. |
| **구독한 피드에서 비슷한 기사 거르기** | 최근 3일 안에 만든 기사와 제목·본문 앞부분의 임베딩 코사인 유사도가 0.82 이상이면 건너뛰기 | 기사 주소·제목이 똑같을 때만 거르기 | 같은 사건을 여러 언론사가 하루 이틀 안에 몰아 쓰고 후속 기사가 2~3일 이어져요. 주소나 제목은 언론사마다 달라서 의미로 비교해야 걸러져요. 3일이면 몰린 기사는 거르고, 일주일 뒤 새 전개는 다시 만들 수 있어요. 비교할 기사가 한 사람의 3일치라 벡터 DB 없이 서버에서 바로 재요. |
| **기사를 만화로 만드는 방법** | 기사를 등장인물 대화로 각색해 녹음 흐름의 받아 적은 대화 자리에 넣기 | 기사 전용 콘티·그림 과정을 따로 만들거나 기사 문장을 그대로 대사로 쓰기 | 장면 고르기·콘티·캐릭터·그림·말풍선·라이브 모드가 모두 대화를 읽도록 맞춰져 있어서, 기사를 대화로 바꾸면 그 뒤를 하나도 고치지 않고 그대로 써요. 기사 문장을 그대로 옮기지 않아 원문 저작권을 지키고, 출처 링크로 원문을 보게 해요. |
| **기사 활용 지침** | 기사에서는 사실만 가져와 새 이야기로 각색하고, 칼럼·사설·인터뷰·사진·영상 기사는 건너뛰고, 맨 아래에 "출처: 언론사명" 한 줄만 남기기. RSS는 확인 후 공개가 기본값 | 기사를 요약하거나 문장을 바꿔 쓰기, 모든 기사를 만들기, 기사 제목과 원문 소개를 크게 보여 주기 | 사건·사실 자체는 저작권으로 보호되지 않지만 기사 문장·제목·구성은 보호될 수 있어요. 사실만 가져와 인물·흐름·대사를 새로 지으면 우리 이야기가 되고, 표현이 핵심인 칼럼·인터뷰는 각색하면 2차적저작물이 될 수 있어 아예 빼요. 실존 인물 명예와 미성년자·피해자 사생활도 지켜요. 출처는 작게 남겨 원문을 존중하고, 자동으로 만든 만화는 사람이 한 번 보고 공개하게 해요. |
| **만화를 몇 컷으로 그릴까** | 콘티를 쓰는 Claude가 이야기에 맞게 4~10컷 중에서 고르기 | 언제나 4컷, 또는 사용자가 컷 수를 고르는 방식 | 짧은 반전은 4컷이 가장 깔끔하지만, 사건이 여러 번 이어지는 대화는 4컷에 넣으면 중요한 순간이 빠졌어요. 이야기를 아는 쪽이 정하는 게 맞아서 사용자에게 묻지 않아요. 컷마다 그림을 한 장씩 그려 시간이 컷 수만큼 늘어나므로 10컷을 넘지 않게 했어요. |
| **GPU PC와 연결하는 방법** | 워커가 일을 가져가는 방식(pull) | 클러스터가 GPU PC를 직접 호출하는 방식 | GPU PC에 포트를 열거나 고정 주소를 둘 필요가 없어요. PC가 꺼져 있어도 일은 대기열에 남아 있다가 켜지면 이어서 처리돼요. |
| **서비스를 얼마나 쪼갤까** | 배포 단위 7개, 생성 과정은 한 서비스 안의 모듈 | 받아 적기·시나리오·만화를 각각 서비스로 (레포 17개, 배포 단위 11개) | 처음 설계는 11개였지만 규모에 비해 운영 부담이 컸어요. 모듈 경계를 테스트로 지키고, 분리가 필요하다는 게 측정으로 확인되면 그때 떼어내요. |
| **작업 대기열** | PostgreSQL 표 + 행 잠금 | Redis나 메시지 큐 서버 추가 | GPU가 한 장이라 한 번에 한 건만 처리하면 돼요. 이미 있는 DB로 충분해서 운영할 서버를 늘리지 않았어요. |
| **캐릭터 검색** | 기존 PostgreSQL에 pgvector 확장 | 별도 벡터 DB | 캐릭터 수만 장 규모는 HNSW 색인 하나로 충분히 빨라요. 데이터가 한곳에 있어 캐릭터 정보와 함께 조회할 수 있어요. |
| **로그인 토큰 보관** | web 서버가 암호화 쿠키로 보관(BFF) | 브라우저 저장소에 토큰 보관 | 브라우저 코드가 토큰에 접근하지 못해 탈취 위험이 줄고, 백엔드 주소도 브라우저에 드러나지 않아요. |
| **LLM을 어디서 돌릴까** | 클라우드 우선 + GPU PC 로컬 모델이 안전망 | 로컬 모델만 사용 | 처음엔 GPU PC의 Qwen3만 썼어요. 콘티 품질과 속도를 위해 Claude·Gemini를 앞에 두고, 로컬 모델은 외부가 모두 막혀도 끝까지 만들도록 남겼어요. |
| **배포** | Argo CD 자동 동기화 | 사람이 태그를 바꾸는 PR과 수동 반영 | 머지만 하면 몇 분 안에 반영돼요. 대신 머지 전 CI(정적 분석, 커버리지 80%)로 품질을 막아요. |
| **그림 모델을 고르는 방법** | 라이선스·16GB 메모리·속도·캐릭터 참조 네 조건을 먼저 거른 뒤, 남은 모델끼리 같은 시험 묶음으로 점수 비교 | 점수가 가장 높은 모델을 그대로 쓰기 | 공개된 모델이라도 상업 사용이 막혀 있거나 조건이 붙은 경우가 많아요. 16GB GPU에 넣으려면 4비트로 줄여야 하는 모델도 많고요. 무엇보다 캐릭터 DB의 그림을 참조해 같은 인물로 그려야 해서, 참조 그림을 받지 못하는 모델은 점수가 높아도 뺐어요. 참조 없이 그린 FLUX.1-schnell은 90.5~91.2점, 참조해서 그린 SDXL은 82.8점이라, 참조할 수 있는 모델끼리 따로 표를 만들어 겨뤘고 FLUX.2 klein 4B(참조해서 92.7점)를 골랐어요. |
| **그림 설명 언어** | 콘티가 그림 설명을 짧은 영어로 씀 | 한국어 설명을 그대로 이미지 모델에 넘김 | 이미지 모델은 앞 77토큰만 읽고 영어로 학습됐어요. 한국어 설명은 잘려서 장면이 사라졌어요. |
| **배경음을 어디서 모을까** | 공개 데이터셋(FSD50K 효과음·환경음, Free Music Archive 음악)에서 CC0·CC BY 클립만 골라 출처·작가·라이선스를 함께 저장 | 생성 모델로 소리 만들기, 또는 라이선스를 가리지 않고 모으기 | 만화에 붙여 내보낼 소리라 상업 사용과 변경이 자유로워야 해요. 비영리(NC)·변경 금지(ND)·동일 조건(SA) 클립은 뺐고, CC BY 클립은 배경음 페이지에 작가와 원본 링크를 보여 줘요. 소리마다 CLAP 모델로 소리 자체의 좌표(512개 숫자)를, BGE-M3로 한국어 설명의 좌표(1,024개 숫자)를 만들어 pgvector에 넣어, 비슷한 소리 찾기와 글로 찾기를 둘 다 할 수 있어요. 한 카테고리에 비슷한 소리를 많이 두기보다 범위를 넓히는 쪽을 골라, 후보 1만 6천여 개 가운데 카테고리마다 서로 다른 소리 몇 개만 남겼어요. 지금 2,852개(환경음 1,194, 효과음 879, 음악 779)가 306개 카테고리에 있어요. |
